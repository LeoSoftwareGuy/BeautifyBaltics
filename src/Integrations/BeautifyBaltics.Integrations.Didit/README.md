# BeautifyBaltics.Integrations.Didit

Integration with [Didit](https://didit.me) for automated identity verification (KYC) of masters.

## How it works

### Overview

Instead of masters uploading documents for manual admin review, 
the entire verification is handled automatically by Didit.
Masters complete ID scanning and a face match on Didit's hosted page. The result is delivered back to our server automatically — no human review needed.

### Full flow

```
1. Master clicks "Start Verification" in the app
         |
         v
2. Our backend calls Didit API to create a session
   POST https://verification.didit.me/v3/session/
   → Didit returns { session_id, url }
   → We store MasterKycVerificationInitiated event (session ID + verification URL)
   → Master's KycStatus is set to Pending
         |
         v
3. Frontend opens the returned URL in a new tab
   (e.g. https://verify.didit.me/session/abc123)
         |
         v
4. Master completes verification on Didit's hosted page
   - ID document scan
   - Live selfie / face match
   (entirely handled by Didit — we build nothing here)
         |
         v
5. Didit posts the result to our webhook
   POST https://our-domain.com/api/v1/webhooks/didit
   { session_id, status: "Approved" | "Declined" | ..., vendor_data: "master-guid" }
         |
         v
6. Our webhook handler processes the result
   - Approved  → MasterKycApproved event  → KycStatus = Approved
   - Declined  → MasterKycRejected event  → KycStatus = Rejected
   - Abandoned/Expired → MasterKycSessionAbandoned → KycStatus = Abandoned (can retry)
         |
         v
7. Master's browser is redirected back to /master/kyc (the callbackUrl we set)
   The page re-fetches master data and shows the updated status
```

### Why two endpoints?

| Endpoint | Called by | Purpose |
|---|---|---|
| `POST masters/{id}/kyc/initiate` | Our frontend | Creates a Didit session, returns the verification URL |
| `POST webhooks/didit` | Didit's servers | Receives the verification result automatically |

The webhook is a standard HTTP POST endpoint — "webhook" just means it is called by an external service rather than our own code. 
It fires server-to-server when Didit finishes verification, regardless of whether the master returns to the app.

### Webhook URL vs. Webhook Secret Key

These are two separate things that are often confused:

- **Webhook URL** — registered manually in the Didit Business Console under API & Webhooks. This is how Didit knows *where* to send the result.
- **WebhookSecretKey** — generated by Didit and copied into our config. This is how *we* verify that an incoming request genuinely came from Didit and is not forged.

On every webhook call Didit includes an `X-Signature-Simple` header: an HMAC-SHA256 hash of `{timestamp}:{session_id}:{status}:{webhook_type}` signed with the secret key.
Our handler recomputes the same hash and rejects the request if they do not match.

### vendor_data

When creating a session we pass `vendor_data = masterId.ToString()`. Didit echoes this back in every webhook payload. 
This is how we know which master a given webhook belongs to — we do not rely on session ID lookups.

## Configuration

Three values are required, all sourced from the Didit Business Console (`business.didit.me`):

```json
"Didit": {
  "ApiKey": "",           // Generated per Application under API & Webhooks
  "WorkflowId": "",       // UUID of the workflow built in Workflow Builder
  "WebhookSecretKey": "", // Generated under API & Webhooks — register webhook URL first
  "BaseUrl": "https://verification.didit.me"
}
```

For **production**: add these as secrets in Azure Key Vault (`Didit:ApiKey`, `Didit:WorkflowId`, `Didit:WebhookSecretKey`).

For **local development**: fill values in `appsettings.Development.json` and expose the backend via a tunnel so Didit can reach it:

```bash
ngrok http https://localhost:{core-api-port}
```

Register the tunnel URL in the Didit Business Console:
```
https://{tunnel-id}.ngrok.io/api/v1/webhooks/didit
```

The `callbackUrl` (where the user's browser is redirected after verification) is read from `AppUrl` in config and does not require a tunnel — it is a browser redirect, not a server call.

## KYC statuses

| Status | Meaning | Can initiate new session? |
|---|---|---|
| `NotSubmitted` | Never started | Yes |
| `Pending` | Session created, verification in progress | No |
| `Approved` | Didit approved — master is visible to clients | No |
| `Rejected` | Didit declined — master can retry (up to workflow limit) | Yes |
| `Abandoned` | User did not complete the session | Yes |
| `Expired` | Session timed out | Yes |

The number of retry attempts on rejection is configured in the Didit workflow, not in our code.

## Key files

| File | Purpose |
|---|---|
| `IDiditService.cs` | Interface: `CreateSessionAsync`, `VerifyWebhookSignature` |
| `DiditService.cs` | Implementation using `HttpClient` |
| `DiditOptions.cs` | Config binding (`Didit` section) |
| `DiditSessionResponse.cs` | Maps Didit's `POST /v3/session/` response |
| `DiditWebhookPayload.cs` | Maps incoming webhook JSON + status constants |
| `ServiceCollectionExtensions.cs` | `AddDiditIntegration()` — registers services and typed `HttpClient` |

Registered in `Program.cs`:
```csharp
builder.Services.AddDiditIntegration(builder.Configuration);
```

Application-layer entry points:
- `Application/Master/Commands/InitiateMasterKycVerification/` — creates the session
- `Application/Master/Commands/ProcessDiditWebhook/` — handles the webhook result
- `Controllers/DiditWebhooksController.cs` — the public webhook endpoint
